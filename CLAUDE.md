# Проект «Склад-СЦ»: индивидуальный учёт автозапчастей

Этот файл читает Claude Code при каждом запуске. Здесь описано, что строим, как устроен
код и как работаем вдвоём. Всё важное о проекте записываем сюда, а не держим в голове
или в чатах.

## Что строим

Веб-систему учёта б/у и новых автозапчастей для нескольких складов и сортировочного центра (СЦ).

Главный принцип: **одна физическая деталь = один индивидуальный SKU**.
100 генераторов из контейнера = 100 SKU. Группировка по наименованию, марке и модели
сохраняется, но каждая деталь живёт своей жизнью: своя бирка, фото, дефекты, ячейка, история.

Проектируем с запасом: несколько складов, десятки одновременных пользователей,
сотни тысяч SKU. Запросы и индексы БД пишем с расчётом на такой объём.

Процесс в СЦ: контейнер принят → дефектовка (**здесь создаётся SKU**) → мойка → фото →
размещение в ячейку → продажа.

> Репозиторий пока публичный. Не пишите сюда названия компаний, имена, адреса, цены,
> пароли и ключи. Внутренние подробности бизнеса храните вне репозитория.

## Стек

- Python 3, **Django 6.1**.
- База: SQLite для разработки, **PostgreSQL** на сервере. Не используем ничего, что
  работает только в SQLite.
- Интерфейс: шаблоны Django + HTMX. Для больших таблиц (группировка, фильтры) позже
  подключим отдельную JS-таблицу (AG Grid Community или аналог).
- Сканирование штрихкодов: через браузер (ТСД или телефон), сканер работает как клавиатура.
- Язык интерфейса: русский (`LANGUAGE_CODE = "ru"`), `TIME_ZONE = "Europe/Moscow"`.

## Структура (целевая)

```
config/        настройки проекта
core/          общие вещи: пользователи, роли, справочники
warehouse/     склады, ячейки, перемещения
parts/         SKU, категории, марки/модели, фото, дефекты, история
sc/            процесс СЦ: контейнеры, приёмка, статусы обработки
sales/         резервы, корзина, продажи (этап 2)
integrations/  выгрузки на площадки, обмен с МоимСкладом (этап 3)
```

## Основные сущности (черновик, уточняется)

- **Склад** (Warehouse, готово): название, код латиницей, тип (склад / СЦ / транзит),
  город, адрес, активен, примечание.
- **Ячейка** (Cell, готово): склад; этаж, зона, стеллаж, ярус, место → из них
  автоматически собирается адрес вида `1.A.12.4.C` (уникален в пределах склада);
  тип (полка, паллет, пол, крупногабарит, буфер); вместимость, шт.; макс. вес, кг;
  штрихкод `C0000123` создаётся сам и не меняется при смене адреса.
  Коды и адреса только латиницей: кириллическая «А» и латинская «A» выглядят
  одинаково, но для сканера это разные символы.
- **Контейнер** (Container): номер, дата прихода, склад приёмки, статус.
- **SKU / Деталь** (Part): уникальный номер бирки (штрихкод), категория (Генератор,
  Стартер…), марка, модель, год, ДВС/маркировка, OEM-номер, состояние, дефекты (текст),
  цена, мин. цена, текущий склад и ячейка, статус, контейнер-источник,
  кто и когда создал.
- **Фото** (PartPhoto): деталь, файл, порядок.
- **Перемещение** (Movement): деталь, откуда (склад/ячейка), куда, кто, когда.
  Каждое перемещение пишется в историю, остатки никогда не меняются «молча».
- **История** (PartEvent): любое изменение статуса, цены, ячейки, с автором и временем.

Статусы СЦ (предварительные, не утверждены):
`Принято → На мойке → На фото → Готово к размещению → Размещено`.
Далее: `В резерве`, `Продано`, `Списано`.

## Роли (предварительно)

- Начальник СЦ: всё по своему СЦ, отчёты.
- Кладовщик-дефектовщик: приёмка, создание SKU, дефекты, печать бирок.
- Кладовщик-фотограф: загрузка фото, перевод в «Готово к размещению».
- Кладовщик склада: размещение и перемещение сканированием.
- Администратор: справочники, пользователи.

## Этапы

1. **MVP для СЦ** (текущий): склады, ячейки, создание SKU на дефектовке, печать бирки
   со штрихкодом, статусы, фото, дефекты, история, перемещение сканированием,
   таблица остатков с поиском и фильтрами.
2. Склад и продажи: остатки по всем складам, резервы, корзина, счета.
3. Интеграции: Авито, Дром, маркетплейсы, МойСклад; роли и права детально.

## Правила кода

- Названия моделей, полей и функций на английском, `verbose_name` и интерфейс на русском.
- Каждое изменение структуры БД оформляется миграцией. Миграции коммитим.
- Деньги: `DecimalField`, не float.
- Удаление деталей запрещено, только статус «Списано».
- Секреты (пароли, ключи) только в `.env`, никогда в коде и в git.
- Перед коммитом: `python manage.py check` и тесты (`python manage.py test`).
- Новая функция = хотя бы простой тест на главный сценарий.

## Работа вдвоём

- Разработчик 1: постановка задач, логика СЦ и склада, интерфейс, проверка.
- Разработчик 2: сервер, PostgreSQL, деплой, HTTPS, бэкапы, мониторинг.
- Код хранится на GitHub (пока публично; позже переезд на свой git-сервер на VPS
  и закрытие доступа). Ветка `main` всегда рабочая.
- Каждая задача делается в своей ветке (`feature/...`, `fix/...`) и сливается через pull request.
- Перед началом работы: `git pull`. После: коммит с понятным описанием по-русски и `git push`.
- Задачи и кто чем занят: файл `TASKS.md` или Issues на GitHub.
- Не правим одновременно одни и те же файлы; договариваемся заранее.
